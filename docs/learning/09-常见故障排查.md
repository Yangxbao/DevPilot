# 09 - 常见故障排查

> 按"症状"组织：先说你看到了什么，再解释为什么，然后给排查命令，最后给修复动作。
> 命令默认在项目根目录执行；Windows 用户可用 Git Bash 或 PowerShell（两者差异处会标注）。
> 配套阅读：`docs/learning/08-关键代码逐步讲解.md`（每类故障背后的代码机制大多在那里有逐行拆解）。

## 1. 后端起不来

### 1.1 JDK 版本不对（17 vs 21）

**现象**：`mvn spring-boot:run` 或 IDEA 启动时报错，典型字样：

```text
UnsupportedClassVersionError: ... has been compiled by a more recent version of the Java Runtime (class file version 65.0)
// 或
[ERROR] Failed to execute goal ... Fatal error compiling: error: release version 21 not supported
```

**原因**：`backend/pom.xml` L21 声明 `<java.version>21</java.version>`（Spring Boot 3.5.16，L9-10），class 文件版本 65 = Java 21。本机装的是 JDK 17（版本 61）就会编译失败或运行时加载失败。

**排查命令**：

```bash
java -version        # 需要 21.x
mvn -v               # 看 "Java version" 一行，Maven 用的 JDK 可能与 java 命令不同
echo $JAVA_HOME      # PowerShell: echo $env:JAVA_HOME
```

**修复**：安装 JDK 21（Temurin/Oracle 均可），把 `JAVA_HOME` 指向它；IDEA 中同时检查 `File → Project Structure → SDK` 与 `Settings → Build Tools → Maven → Runner → JRE`。多版本共存时可用 `JAVA_HOME=/path/to/jdk-21 mvn spring-boot:run` 临时切换。

### 1.2 端口占用（8080）

**现象**：启动日志出现：

```text
Web server failed to start. Port 8080 was already in use.
```

**原因**：8080 上已有进程（最常见：上一个没杀干净的后端、或其它 Java/Tomcat 服务）。后端端口由 `application.yml` L2 `server.port: ${SERVER_PORT:8080}` 决定，可用环境变量覆盖。

**排查命令**：

```bash
# Windows（Git Bash / PowerShell 均可）
netstat -ano | grep :8080        # PowerShell 可用: netstat -ano | findstr :8080
tasklist | grep <上一步的PID>
# 杀掉旧进程
taskkill //PID <PID> //F         # 注意 Git Bash 里要写双斜杠
```

**修复**：杀掉占用进程，或换端口启动：`SERVER_PORT=8090 mvn spring-boot:run`（换端口后 `frontend/vite.config.ts` 的代理目标 `http://127.0.0.1:8080` 也要同步改）。

### 1.3 MySQL 连不上

**现象**：启动即失败，日志含：

```text
HikariPool-1 - Connection is not available, request timed out after 5000ms.
// 或
Communications link failure ... The last packet sent successfully to the server was 0 milliseconds ago.
```

**原因**：默认连接串在 `application.yml` L8：`jdbc:mysql://127.0.0.1:3307/devpilot?...`——注意端口是 **3307**。而 `docker-compose.yml` 里 MySQL 容器映射的是 `3306:3306`。两种正确姿势选一种，混用必挂：

- 用 docker-compose 的 MySQL（3306）→ 必须设 `DB_URL` 覆盖默认 3307；
- 用本机自装 MySQL（开发者环境监听 3307）→ 直接用默认值。

另外三个常见子原因：账号密码不对（`DB_USERNAME`/`DB_PASSWORD`，compose 默认 `devpilot/devpilot123`）、`devpilot` 库不存在（compose 会自动建库 `MYSQL_DATABASE: devpilot`，自装库需手动 `CREATE DATABASE devpilot CHARACTER SET utf8mb4`）、MySQL 容器还在启动中（compose 有 healthcheck，等 `docker compose ps` 显示 healthy）。

**排查命令**：

```bash
docker compose ps                          # mysql 是否 Up (healthy)
docker compose logs mysql --tail 30        # 容器内启动日志
# 测连通性（端口对不对一试便知）
mysql -h 127.0.0.1 -P 3307 -u root -p -e "SELECT 1;"   # 默认配置假设的端口
mysql -h 127.0.0.1 -P 3306 -u root -p -e "SELECT 1;"   # compose 的端口
```

**修复**：对齐端口。例如用 compose 数据库时：

```bash
export DB_URL='jdbc:mysql://127.0.0.1:3306/devpilot?useUnicode=true&characterEncoding=utf8&serverTimezone=Asia/Shanghai&useSSL=false&allowPublicKeyRetrieval=true&rewriteBatchedStatements=true'
export DB_USERNAME=devpilot DB_PASSWORD=devpilot123
mvn spring-boot:run
```

### 1.4 Flyway 校验失败

**现象**：

```text
Validate failed: Migration checksum mismatch for migration version 1
// 或
Validate failed: Migrations have failed validation - detected resolved migration not applied to database
```

**原因**：`application.yml` L16-19 开启了 Flyway（`baseline-on-migrate: false`）。校验失败几乎总是两种情况之一：有人改了 `V1__init.sql` 的内容（checksum 对不上），或库里被手动改过结构/建了不一致的表。

**排查命令**：

```bash
mysql -h 127.0.0.1 -P <端口> -u <用户> -p -e "SELECT version, checksum, success FROM devpilot.flyway_schema_history;"
```

**修复**：开发期最简单的恢复方式——库是可重建的（代码数据不在 MySQL，索引在 Python 侧 SQLite，均为派生数据）：

```bash
mysql ... -e "DROP DATABASE devpilot; CREATE DATABASE devpilot CHARACTER SET utf8mb4;"
mvn spring-boot:run    # Flyway 重新执行 V1__init.sql
```

生产思路（本项目未部署生产，仅作方法论）：改历史脚本是大忌，应新增 `V2__xxx.sql`；确需重置必须连带评估数据迁移。

## 2. 索引任务 FAILED：原因分类与日志位置

**日志位置**：`backend/logs/devpilot-backend.log`（`application.yml` L84-89 `logging.file.name: logs/devpilot-backend.log`，相对后端工作目录）。索引相关错误搜 `索引完成`、`AI 服务`、`ImportAbortedException`、`索引任务异常`。

任务失败时：`index_task.status=FAILED` 且 `error_message` 有值，前端任务详情页（`GET /api/v1/index-tasks/{id}`）可直接看到原因。失败原因与代码的对应关系（完整机制见 08 篇第 ② ③ ④ 节）：

| `error_message` 关键字 | 真实出处 | 含义 |
|---|---|---|
| "压缩包条目数超过上限 8000" / "解压总量超过上限 200MB" / "文件数超过上限" / "仓库总大小超过上限" | `ImportService` L40-43, L82-84, L94-97, L166-171 | 触发了三重导入上限，属预期保护 |
| "压缩包读取失败" / "找不到已上传的压缩包" | `ImportService` L72-74, L101-106 | zip 文件缺失或损坏 |
| "git clone 失败/超时（>120s）" | `ImportService` L122-149 | git 导入路径问题（仅 https 公开仓库受支持） |
| "AI 服务不可用，语义索引未建立（关键词检索不受影响）" | `AiIndexClient` L85-88 | Python 服务没起或 reindex 失败；**此时文件/分块已入库，关键词检索照常可用**（`AsyncIndexRunner` L92-96 特意把仓库 importStatus 保持 SUCCESS） |
| "仓库不存在或已删除" | `AsyncIndexRunner` L47-50 | 任务触发后仓库被删 |
| "索引执行异常: <异常类名>" | `AsyncIndexRunner` L97-102 | 未知异常，需查日志堆栈 |

**排查命令**：

```bash
# 看任务表里到底记了什么
mysql -h 127.0.0.1 -P <端口> -u <用户> -p -e \
  "SELECT id, status, error_message, total_files, processed_files, total_chunks FROM devpilot.index_task ORDER BY id DESC LIMIT 5;"
# 看后端日志对应的完整堆栈
grep -A 20 "索引任务异常\|reindex 调用失败" backend/logs/devpilot-backend.log | tail -60
# 若怀疑 Python 侧：直接探活
curl http://127.0.0.1:8200/health
```

**修复**：按 `error_message` 对号入座——上限类说明仓库太大需要裁剪；"AI 服务不可用"先按第 6 节把 Python 服务救活，再重新触发索引（active 唯一索引保证 FAILED 任务不会挡新任务）；unknown 异常拿日志堆栈继续追。

## 3. 语义检索 vectorEnabled=false 的排查顺序

**现象**：搜索接口（`GET /api/v1/search?mode=semantic`）返回 `"vectorEnabled": false`，或 Agent 轨迹里 `retrieve` 步骤 detail 显示 `vector=False`。

先理解"哪里会把它置 False"——只有两处：

1. **索引期**：`store.upsert_chunks`（`store.py` L84-88）embedding 失败 → 该批 chunk 全部没有向量 → `has_vectors` 为 False（`store.py` L149-152）。Java 侧 `AiIndexClient.reindex` L81 用 AND 聚合如实上报。
2. **检索期**：`retrieval.search`（`retrieval.py` L80-83）对查询文本做 embedding 失败 → 当场降级关键词。

**排查顺序（由外到内）**：

```bash
# 第 1 步：Python 服务活着吗？provider 是什么？
curl http://127.0.0.1:8200/health
# 期望: {"status":"UP","llmProvider":"mock","embeddingProvider":"hashing","vectorReady":true}
# embeddingProvider 若是 "openai"，说明走远程 API——失败概率集中在网络/Key/配额

# 第 2 步：索引期有没有降级？看触发索引那一刻的日志
grep "embedding 不可用" ai-service.log          # store 降级时 main.py L58-59 会打 warning
grep "vector=" backend/logs/devpilot-backend.log

# 第 3 步：用最直白的 API 验证一次检索
curl -X POST http://127.0.0.1:8200/internal/search \
  -H "X-Internal-Token: dev-internal-token" -H "Content-Type: application/json" \
  -d '{"repositoryId":1,"query":"login","topK":5,"mode":"semantic"}'
# 响应里 vectorEnabled=false → 证据坐实；channel 字段全为 keyword → 向量通道没参与

# 第 4 步（embeddingProvider=openai 时）：手动验证 embedding 接口连通性
curl -s $EMBEDDING_BASE_URL/embeddings -H "Authorization: Bearer $EMBEDDING_API_KEY" \
  -H "Content-Type: application/json" -d '{"model":"text-embedding-3-small","input":["hi"]}'
```

**修复**：

- 想先跑通：保持 `EMBEDDING_PROVIDER=hashing`（默认，本地零依赖，`config.py` L20）。hashing 向量质量有限但**诚实可用**——UI/响应字段不会宣称它是真实语义向量。
- 想要真语义：配 `EMBEDDING_PROVIDER=openai` + `EMBEDDING_API_KEY`（`embeddings.py` L91-99），然后**必须重新触发索引**——已入库的 chunk 没有向量，重新索引才有。注意：`vector_search`（`store.py` L134-147）是全表余弦扫，维度不一致的向量（hashing 256 维 vs openai 1536 维）混存会导致 `_cosine` 直接返回 0 分，全量重建是唯一正确做法。

## 4. 前端登录后 401 循环

**现象**：登录成功跳转后，每个请求都 401，被 `http.ts` 拦截器（L30-36）踢回登录页，再次登录又循环。

**原因与排查**（按概率排序）：

1. **JWT secret 变了**：`application.yml` L66 默认 `dev-only-secret-key-please-override-in-prod-0123456789`，若用 `JWT_SECRET` 环境变量覆盖且两次启动值不同，旧 Token 全部验签失败。`JwtService` L32-35 还要求 secret ≥ 32 字节，太短会直接启动失败。→ 对比两次启动的 `JWT_SECRET`。
2. **Token 真过期**：默认 120 分钟（`expire-minutes: 120`）。→ 看 Token 的 `exp`（浏览器控制台 `atob(localStorage.getItem('devpilot_token').split('.')[1])`）。
3. **用户被禁用**：`JwtAuthFilter` L54-61 每次请求回库校验 `status==1`，禁用后即使 Token 有效也 401。→ 查 `sys_user.status`。
4. **走了登出**：jti 进了黑名单（`JwtAuthFilter` L45-50）。→ 重新登录即可。

**排查命令**（浏览器 DevTools → Network → 任一 401 请求 → Request Headers）：

```text
Authorization: Bearer eyJ...        # 存在吗？三段结构吗？
# 后端日志
grep "非法或过期的 Token" backend/logs/devpilot-backend.log
```

**修复**：统一 `JWT_SECRET`（写进 `.env` 或启动脚本）；前端清 `localStorage` 后重新登录。特别说明：`http.ts` 的守卫（L34 判断当前路由是否已是 login）已防止**登录页自身**触发循环，出现循环说明 401 来自登录后的业务请求，重点查第 1、3 条。

## 5. 跨域（CORS）报错

**现象**：浏览器控制台：

```text
Access to XMLHttpRequest at 'http://127.0.0.1:8080/api/v1/...' from origin 'http://localhost:5173'
has been blocked by CORS policy: Response to preflight request doesn't pass access control check
```

**原因**：浏览器同源策略。但注意——**开发态正常部署不该遇到它**：`frontend/vite.config.ts` 把 `/api` 代理到 `http://127.0.0.1:8080`，前端只请求自己的 5173 源，浏览器视角全程同源。会报 CORS，通常是你做了以下之一：

- 前端直连后端（把 baseURL 改成了绝对地址，或页面不是从 5173 打开的）；
- 后端 `CORS_ORIGINS` 白名单没包含当前来源（`application.yml` L75-76，默认 `http://localhost:5173,http://127.0.0.1:5173`，经 `SecurityConfig`/`WebConfig` L72 注册）；
- 请求经了别的反向代理且代理层没转发 `Origin` 头。

**排查命令**：

```bash
# 直接看预检响应头（Origin 必须在白名单里）
curl -i -X OPTIONS http://127.0.0.1:8080/api/v1/auth/login \
  -H "Origin: http://localhost:5173" -H "Access-Control-Request-Method: POST" \
  -H "Access-Control-Request-Headers: content-type"
# 期望响应含: Access-Control-Allow-Origin: http://localhost:5173
```

**修复**：最推荐——回到同源代理（确认浏览器访问的是 `http://localhost:5173` 而非直连 8080）；确需跨域时把来源加进 `CORS_ORIGINS`（逗号分隔、含协议与端口、不要结尾斜杠）。

## 6. Python 服务 503（LLM 不可用）

**现象**：问答/Bug 分析返回 50200（"AI 服务调用失败"），Python 日志（`ai-service.log` 或控制台）出现 `qa LLM 不可用: ...`。

**原因链**：`llm.py` 的 `OpenAIChatLLM.generate`（L98-128）对 5xx/429 退避重试 2 次后抛 `LLMUnavailable`；`main.py` L119-121 / L135-137 捕获后映射 **HTTP 503**。`build_llm`（L131-142）还有一个必中陷阱：`LLM_PROVIDER=openai` 但没配 `LLM_API_KEY` → 启动后第一次调用立刻 503。

**排查命令**：

```bash
curl http://127.0.0.1:8200/health          # 服务活着吗？llmProvider 是什么？
grep "LLM 不可用" ai-service.log | tail -5  # 具体错误：超时？401？配额？
# provider=openai 时手动测上游
curl -s $LLM_BASE_URL/chat/completions -H "Authorization: Bearer $LLM_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{"model":"gpt-4o-mini","messages":[{"role":"user","content":"hi"}]}' | head -c 500
```

**修复**：

- 忘配 Key：补 `LLM_API_KEY`，或把 `LLM_PROVIDER` 改回 `mock`（默认值，离线可跑，输出带"演示模式"徽标）。
- 超时（默认单次 60s，`config.py` L16）：网络慢可调大 `LLM_TIMEOUT_SECONDS`，但注意 Java 侧 Agent 等待上限 150s（`application.yml` L74），Python 侧不要调出比它更长的总时长。
- 上游限流/宕机：等恢复或换 provider；503 语义即"上游不可用"，前端与 Java 都按此提示，不静默降级编造答案——这是设计使然。
- **诚实标注**：`LLM_PROVIDER=openai` 的真实调用链路在自动化测试中**未验证**（测试环境无 Key，31 项 pytest 全部跑 Mock），接入真实 Key 后建议先用 `curl` 直测上游再做端到端验证。

## 7. 中文检索不到词（FTS5 分词 / bigram）

**现象**：英文（如 `login`、`UserService`）能搜到，中文关键词（如"登录"）零结果，或只有部分词能搜到。

**原因**：SQLite FTS5 默认 `unicode61` 分词器**不支持 CJK 词组**——连续汉字被当作一个超长 token，任何短词都匹配不上。DevPilot 的解法是 CJK bigram（`store.py` L38-47）：索引与查询**两侧**都把连续汉字滑窗切成交叠二元组（"登录接口" → `登录 登接 接口`）。由此派生三条规则，排障全靠它们：

1. **两侧必须对称**：写入走 `cjk_bigrams`（L109），查询也必须走（`keyword_search` L117）。如果你绕过 `/internal/search` 自己拼 SQL，就会一侧 bigram 一侧原文，永远查不到。
2. **单字查不到**：正则 `[\u4e00-\u9fff]{2,}` 只处理 ≥2 字的串，单个汉字（如搜"码"）不产 bigram——这是已知边界。
3. **词必须 ≥2 字相邻出现**：bigram 只保留原始相邻关系，跨字距的语义联想是向量通道的活（若 hashing embedding，同义能力有限）。

**排查命令**：

```bash
# 直接进 Python 侧的 SQLite 验证索引内容（Windows 下先确认服务未占用该文件，见第 8 节）
sqlite3 ai-service/data/index-store/repo-1.sqlite \
  "SELECT chunk_id, substr(content,1,40) FROM chunks_fts WHERE content LIKE '%登录%';"
# 再看分词后实际存了什么
sqlite3 ai-service/data/index-store/repo-1.sqlite "SELECT substr(content,1,60) FROM chunks_fts LIMIT 5;"
# 走正规 API 对比（keyword_search 会对查询做 bigram）
curl -X POST http://127.0.0.1:8200/internal/search \
  -H "X-Internal-Token: dev-internal-token" -H "Content-Type: application/json" \
  -d '{"repositoryId":1,"query":"登录","topK":5,"mode":"keyword"}'
```

**修复**：

- 索引里根本没有该中文内容 → 先重新索引（中文内容是否入库可用 `code_file` 表核对）。
- 查询词太短（单字）→ 换 ≥2 字词，或换语义模式。
- 自己直连 SQLite 调试 → 查询文本记得同样做 bigram，或干脆走 `/internal/search`。
- 验证参照物：`test_api.py` L36-54 的 roundtrip 用例（中文 README 入索引后用中文问题命中）证明该机制在默认配置下工作正常。

## 8. Windows 下 SQLite 文件占用

**现象**：删除/重建仓库索引时报错，日志类似：

```text
PermissionError: [WinError 32] The process cannot access the file because it is being used by another process: '...repo-1.sqlite'
```

**原因**：`store.py` 模块 docstring L8 早已写明：*"连接管理：Windows 下必须显式 close，否则文件句柄占用会导致 clear 失败"*。Windows 的文件锁是强制性的——只要有一个 SQLite 连接未关闭，`clear()` 里的 `os.remove`（L61-64）就删不掉文件。代码里所有连接都用 `with closing(...)`（L67, L91, L121, L135）保证用完即关；出问题通常来自**代码之外**的持有者。

**排查命令**：

```powershell
# 谁占着文件？（PowerShell，需 Sysinternals handle.exe 或资源监视器）
handle.exe repo-1.sqlite
# 或资源监视器 (resmon) → CPU 标签 → 关联的句柄 → 搜索 "repo-1.sqlite"
# 最常见持有者：正在运行的 ai-service（uvicorn 调试进程）、或你自己开的 DB 工具
netstat -ano | findstr :8200    # 8200 上有没有残留的 ai-service
```

**修复**：

## 通用排障心法

1. **先定位层**：浏览器 F12 网络面板看状态码——401 查认证（第 4 节）、403 查权限、409 查状态冲突（如重复索引任务）、50200 查 Java→Python 链路（第 2/6 节）、503 查 LLM（第 6 节）。
2. **日志顺序**：`backend/logs/devpilot-backend.log`（Java 侧全程留痕）→ `ai-service.log`（Python 侧）→ `docker compose logs`（基础设施）。索引/AI 请求在 Java 日志里都有 `repoId`/`analysisId` 可串。
3. **派生数据大胆重置**：MySQL 的代码表、Python 的 SQLite、仓库克隆目录全是可重建的派生数据；用户/项目/缺陷/分析记录才是主数据。排障卡死时"清派生、保主数据、重新索引"往往最快。
4. **测试事实基线**：以上机制在默认配置（mock LLM + hashing embedding）下有自动化测试兜底——ai-service 31 项 pytest、后端 20 项集成测试、E2E 18 项全部通过；真实 LLM 调用与 Docker Compose 部署未纳入自动化验证，遇到问题请按第 3/6 节手动验证上游连通性。
