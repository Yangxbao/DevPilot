## ① JwtAuthFilter.doFilterInternal：一次认证的完整代码路径

文件：`backend/src/main/java/com/devpilot/security/JwtAuthFilter.java`（L37-69）

```java
@Override
protected void doFilterInternal(HttpServletRequest request, HttpServletResponse response,
                                FilterChain filterChain) throws ServletException, IOException {
    String header = request.getHeader("Authorization");                    // (1)
    if (StringUtils.hasText(header) && header.startsWith("Bearer ")) {     // (2)
        String token = header.substring(7);
        try {
            Claims claims = jwtService.parse(token);                       // (3)
            String jti = claims.getId();
            if (jti != null && tokenBlacklist.contains(jti)) {             // (4)
                filterChain.doFilter(request, response);                   // (5)
                return;
            }
            Long uid = claims.get("uid", Long.class);
            String role = claims.get("role", String.class);
            if (uid != null && role != null) {
                SysUser user = userMapper.selectById(uid);                 // (6)
                if (user != null && user.getStatus() != null && user.getStatus() == 1) {  // (7)
                    UserPrincipal principal = new UserPrincipal(user.getId(), user.getUsername(), user.getRole());
                    UsernamePasswordAuthenticationToken authentication = new UsernamePasswordAuthenticationToken(
                            principal, null, List.of(new SimpleGrantedAuthority("ROLE_" + user.getRole())));  // (8)
                    authentication.setDetails(new WebAuthenticationDetailsSource().buildDetails(request));
                    SecurityContextHolder.getContext().setAuthentication(authentication);  // (9)
                }
            }
        } catch (JwtException | IllegalArgumentException e) {              // (10)
            log.debug("非法或过期的 Token: {}", e.getMessage());
        }
    }
    filterChain.doFilter(request, response);                               // (11)
}
```

**逐行解释**：

- (1)(2)：取 `Authorization` 头并要求 `Bearer ` 前缀。没有头的请求（如登录接口）直接走 (11)，以匿名身份继续。
- (3)：`JwtService.parse`（`JwtService.java` L56-57）做**签名 + 过期时间**双重校验，任何问题抛 `JwtException`。
- (4)(5)：解析成功还要查 `jti`（Token 唯一 ID）是否在黑名单——这是"登出后 Token 立即失效"的实现（`/auth/logout` 会把 jti 写入黑名单，见 API_CONTRACT 1.1）。命中黑名单**保持未认证**继续放行，最终由授权规则返回 401。
- (6)(7)：**回库查用户**。JWT 是自包含的，但代码仍然每次请求查一次数据库——换来一个关键能力：**用户被禁用（status != 1）或删除后，已签发的 Token 立即失效**，不用等 2 小时过期（`application.yml` L67 `expire-minutes: 120`）。
- (8)(9)：把用户包装成 Spring Security 认识的 `UsernamePasswordAuthenticationToken`（权限前缀 `ROLE_` + 角色名，后续 `hasRole('ADMIN')` 之类规则都基于它），再写入 `SecurityContext`——这一行执行完，本次请求在后续任何代码里都是"已认证"状态（`SecurityUtils.current()` 就是从这里取的）。
- (10)：**任何解析失败都不抛异常**，只打 debug 日志。类注释（L25-26）写明了原则：*"任何解析失败都不抛异常，请求以匿名身份继续，由授权规则返回 401"*。
- (11)：无论认证成功与否，过滤器链继续。

**设计动机**：过滤器只负责"识别你是谁"（Authentication），"你能不能访问"（Authorization）交给 `SecurityConfig`（L45-50：登录/注册、健康检查、Swagger 为 permitAll，其余 anyRequest().authenticated()）。职责分离后，401 的语义永远由授权层统一给出。

**如果去掉会怎样**：
- 去掉 (6)(7)：被禁用用户在 Token 有效期内仍可横行 2 小时。
- 去掉 (4)：登出形同虚设，Token 泄露后无法止损。
- 把 (10) 改成向上抛异常：每个没带 Token 的公开请求（如 `/actuator/health`）都会 500，探活直接挂。

## ② index_task.active 唯一索引：用数据库防并发重复任务

文件：`backend/src/main/resources/db/migration/V1__init.sql`（L105-128）、`backend/src/main/java/com/devpilot/module/indexing/IndexTaskService.java`（L40-64, L89-100）、`AsyncIndexRunner.java`（L176-186）

**逐行解释**：

- (1)(2)：先查有没有 `active=1` 的在途任务，有就 409（`code=40900`），并附上任务号方便用户去页面看进度。
- (3)(4)(5)(6)：`active` 设为 1 后插入。**查询检查是给用户看友好提示的，真正的防线是 (5)**：两个请求同时通过 (1) 的检查（check-then-act 竞态），第二个 insert 会撞 `uk_repo_active` 唯一索引，Spring 翻译成 `DuplicateKeyException`，被捕获后同样返回 409——数据库约束是唯一不会说谎的裁判。插入成功后才异步执行（`@Async("indexExecutor")`，`AsyncIndexRunner` L40-41），HTTP 响应秒回。
- (7)：**本段最精妙的一行**。任务进入终态（SUCCESS/FAILED）时把 `active` 置为 `NULL`——MySQL 的唯一索引对 NULL 有豁免（`NULL != NULL`），所以历史任务可以无限多条；只有"进行中"的 `active=1` 受唯一性保护。注释也点破了 MyBatis-Plus 的坑：update 默认**跳过 null 字段**，必须用 `LambdaUpdateWrapper.set(..., null)` 显式写。

**设计动机**：分布式任务防重的选项有 Redis 锁、定时清理僵尸任务等，都需要额外组件和心跳逻辑。这里利用"`NULL 可重复`"这一 SQL 标准行为，用一条 DDL 就实现了幂等的并发闸门，且**崩溃安全**——进程被杀时 active 任务留在库里，恰好阻止新任务与"未知状态"并发。

**如果去掉会怎样**：用户双击"重新索引"按钮 → 两个异步任务同时导入/清空/推送同一仓库 → Python 侧 `clear` 与 `upsert` 交错，索引半新半旧，甚至互相删库。`AsyncIndexRunner.executeTask` L43-44 的 `!"PENDING".equals(task.getStatus())` 再检查也只能挡住顺序重放，挡不住毫秒级并发。

## ③ ImportService.readEntry：流式限额读取，防压缩包炸弹

文件：`backend/src/main/java/com/devpilot/module/indexing/ImportService.java`（L194-210，常量 L40-43）

```java
public static final int MAX_ENTRIES = 8000;             // 条目数上限
public static final long MAX_TOTAL_BYTES = 200L * 1024 * 1024;   // 解压总量 200MB
public static final long MAX_FILE_BYTES = 512L * 1024;  // 单文件 512KB
...
private ImportedFile readEntry(ZipFile zipFile, ZipEntry entry, String safePath) {
    try (var in = zipFile.getInputStream(entry)) {
        byte[] head = in.readNBytes(8192);                                // (1)
        if (Chunker.looksBinary(head)) {                                  // (2)
            return new ImportedFile(safePath, "", head.length, 0, null, "binary");
        }
        // 不信任条目声明大小（流式 zip 可能为 -1 或伪造），读取时强制限额
        byte[] rest = in.readNBytes((int) (MAX_FILE_BYTES + 1 - head.length));  // (3)
        byte[] all = concat(head, rest);
        if (all.length > MAX_FILE_BYTES) {                                // (4)
            return new ImportedFile(safePath, "", all.length, 0, null, "too_large");
        }
        return buildTextFile(safePath, all);
    } catch (IOException e) {
        return new ImportedFile(safePath, "", 0, 0, null, "read_error");   // (5)
    }
}
```

**逐行解释**：

- (1)：先读 8KB 头部用于二进制探测。
- (2)：`looksBinary` 判定为二进制（图片/字体/编译产物）→ 跳过解析，记 `skipReason="binary"`。这个跳过原因会一路存进 `code_file.skip_reason`，用户能在文件清单接口（API_CONTRACT 1.3 `/repositories/{id}/files`）里看到**为什么这个文件没被索引**。
- (3)：**本段核心**。`ZipEntry.getSize()` 返回的是 zip 元数据里"声明"的大小，可以被伪造（声明 1 字节、实际展开 10GB——这就是压缩包炸弹）。所以代码**不看声明，只看实际读到的字节数**：`readNBytes(MAX_FILE_BYTES + 1)` 最多读 512KB **再加 1 字节**。
- (4)(5)：那多出来的 1 字节就是"超限探测器"——读到 512KB+1 说明文件超限，记 `too_large` 跳过（多读 1 字节而非读完再判断，保证内存占用永远有界）；单个文件读失败**不炸整个导入**，降级为 `read_error` 记录继续。

外层还有两道总量闸门（`importFromUpload` L82-84 与 L94-97）：条目数超过 8000、累计字节数超过 200MB，都抛 `ImportAbortedException` 让整个任务 FAILED。

**设计动机**：用户上传的 zip 是典型的**不可信输入**。10MB 的 zip 可以解压出几十 GB（高压缩比炸弹），足以打爆内存或磁盘。三重上限（条目数/总量/单文件）+ 流式读取 + 不信任声明大小，组合起来让最坏情况的资源消耗变成**可计算的常数**。

**如果去掉会怎样**：一个恶意或误压缩的 zip 就能让后端 OOM 或写满磁盘，且发生在异步线程里——用户只会看到服务"悄悄变慢然后死掉"，日志里可能连异常都来不及打。

## ④ AiIndexClient.reindex：分批推送语义索引

文件：`backend/src/main/java/com/devpilot/module/ai/AiIndexClient.java`（L35, L65-89, L151-157）

```java
private static final int REINDEX_BATCH_SIZE = 200;

/** 全量重建索引：先清空再分批推送，返回是否启用了向量检索 */
public boolean reindex(Long repositoryId, List<ChunkPayload> chunks) {
    try {
        deleteIndex(repositoryId);                                     // (1)
        boolean vectorEnabled = true;                                  // (2)
        List<List<ChunkPayload>> batches = partition(chunks, REINDEX_BATCH_SIZE);  // (3)
        for (List<ChunkPayload> batch : batches) {
            Map<String, Object> body = new HashMap<>();
            body.put("repositoryId", repositoryId);
            body.put("chunks", batch);
            ReindexResult result = searchClient.post()
                    .uri("/internal/reindex")
                    .contentType(MediaType.APPLICATION_JSON)
                    .body(body)
                    .retrieve()
                    .body(ReindexResult.class);
            if (result != null) {
                vectorEnabled = vectorEnabled && result.vectorEnabled();  // (4)
            }
        }
        return vectorEnabled;                                          // (5)
    } catch (RestClientException e) {
        log.warn("AI 服务 reindex 调用失败 repoId={}: {}", repositoryId, e.getMessage());
        throw new BizException(ErrorCode.UPSTREAM_ERROR, "AI 服务不可用，语义索引未建立（关键词检索不受影响）");  // (6)
    }
}

private static <T> List<List<T>> partition(List<T> list, int size) {   // (7)
    List<List<T>> parts = new ArrayList<>();
    for (int i = 0; i < list.size(); i += size) {
        parts.add(list.subList(i, Math.min(i + size, list.size())));
    }
    return parts;
}
```

**逐行解释**：

- (1)(2)：先 `DELETE /internal/index/{repositoryId}` 清空旧索引（对应 Python 侧 `store.clear`，删除整个 SQLite 文件），保证"全量重建"语义——不会残留上一次索引的僵尸 chunk。`vectorEnabled` 初始为 true，后面做**AND 聚合**。
- (3)(7)：`partition` 按 200 个 chunk 一批切分。为什么是 200：Python 侧契约单请求上限 500 chunk（`schemas.py` L29 `chunks: list[ChunkIn] = Field(max_length=500)`），且每批 embedding 计算（纯 Python 余弦或远程 API）都耗时，200 是"请求不至于过大、批次数不至于过多"的折中。
- (4)：每一批的响应里带 `vectorEnabled`——Python 侧 `upsert_chunks`（`store.py` L84-88）embedding 失败时给该批全部置 `vector_enabled=False`。**只要有一批降级，整体就如实报告降级**（AND 语义），绝不"部分向量也宣称全量向量可用"。
- (6)：任何网络/HTTP 失败统一转 `BizException(UPSTREAM_ERROR)`，消息明确说"语义索引未建立（关键词检索不受影响）"——错误信息本身就在教用户接下来该怎么办。调用方 `AsyncIndexRunner` L92-96 捕获后：**导入已成功的文件/分块保留在 MySQL（关键词检索照常可用），仅索引任务记 FAILED**。

**设计动机**：一次 HTTP 请求体太大会撞 multipart/JSON 上限、占双端内存、且失败后全部重来；分批让每次失败只损失一批，也让进度可观测。AND 聚合 + 诚实降级，与 07 篇讲的 Embedding 降级策略一脉相承。

**如果去掉会怎样**：不分批 → 大仓库一个请求几百 MB，Python 序列化/embedding 时长超 Java 15s 读超时（`application.yml` L73），任务必然 FAILED；去掉 (1) → 反复索引同一仓库会在 SQLite 里累积重复 chunk（`chunk_id` 变了，旧 chunk 永远检索得到）；去掉 (4) 的 AND → 某批 embedding 挂了用户却在 UI 上看到"向量检索已开启"，语义模式搜索时莫名缺结果，排障无从下手。

## ⑤ retrieval.search：RRF 融合公式

文件：`ai-service/app/retrieval.py`（L13, L52-97）

```python
RRF_K = 60

def search(store, repository_id, queries, top_k, mode, embedding_provider):
    """多查询混合检索。mode: keyword | semantic | hybrid。返回 (去重后的证据, vector_enabled)。"""
    vector_enabled = store.has_vectors(repository_id)                 # (1)
    rrf: dict[str, float] = {}
    rows: dict[str, dict] = {}
    channels_of: dict[str, set[str]] = {}

    def add(channel: str, hits: list[dict]) -> None:                  # (2)
        for rank, row in enumerate(hits):
            cid = row["chunk_id"]
            rows[cid] = row
            channels_of.setdefault(cid, set()).add(channel)
            rrf[cid] = rrf.get(cid, 0.0) + 1.0 / (RRF_K + rank + 1)   # (3)

    for query in queries:
        if not query.strip():
            continue
        if mode in ("keyword", "hybrid"):
            add("keyword", store.keyword_search(repository_id, query, top_k))   # (4)
        if mode in ("semantic", "hybrid") and vector_enabled:
            try:
                qvec = embedding_provider.embed_batch([query])[0]
            except EmbeddingUnavailable:
                vector_enabled = False                                # (5)
                qvec = None
            if qvec is not None:
                add("vector", store.vector_search(repository_id, qvec, top_k))

    if mode == "semantic" and not vector_enabled:
        for query in queries:                                         # (6)
            add("keyword", store.keyword_search(repository_id, query, top_k))

    ordered = sorted(rrf.items(), key=lambda item: item[1], reverse=True)[: max(top_k * 2, 10)]  # (7)
    evidence = []
    for cid, score in ordered:
        channels = "+".join(sorted(channels_of[cid]))
        evidence.append(_to_evidence(rows[cid], score, channels))
    return evidence, vector_enabled
```

**RRF 公式本身**（行 3）：

```
score(chunk) = Σ_channels  1 / (60 + rank_i)
```

- `rank_i` 从 0 开始（所以分母是 60 + rank + 1，即第 1 名得 1/61）。
- 一个 chunk 如果**同时**被关键词和向量通道命中，两个通道的倒数排名分**累加**，天然排到最前——这就是"混合检索优于单通道"的数学表达。
- `RRF_K=60` 是平滑常数：让第 1 名与第 2 名的分差不至于悬殊，且不同通道的分数尺度（FTS5 的 bm25 分数与余弦相似度**不可直接比较**）被归一成统一的"排名倒数"。

**逐行解释**：

- (1)：先探测该仓库是否有向量（`has_vectors`，`store.py` L149-152，查 `embedding IS NOT NULL` 的行数），避免每个 query 都白算一次 embedding。
- (2)(3)：内嵌函数 `add` 是全部融合逻辑——按通道给出的有序命中列表，逐个累加 `1/(60+rank+1)`。三个字典分别存分数、原始行、命中通道集合。
- (4)(5)：混合模式下双通道并行尝试；embedding 挂了**当场降级**为纯关键词，`vector_enabled` 如实变 False 并随响应返回。
- (6)(7)：语义模式整体不可用时兜底跑关键词——用户拿到的是"能用但退化的结果"而非报错，且调用方从返回值知道发生了什么。最终按 RRF 分排序，取 `max(top_k*2, 10)` 条——**比 top_k 多取一倍**，给下游 Agent 的证据预算（12 块）留余量，也让单通道命中但排名靠后的证据有机会入围。

**设计动机**：关键词通道擅长精确符号（类名 `UserService`），向量通道擅长语义（"登录逻辑"能命中 `login` 函数），但两者的原始分数量纲不同无法加权。RRF 只用**排名**不用分值，天然免归一化，是 2009 年起信息检索领域验证过的最简健壮融合方案。

**如果去掉会怎样**：只留关键词 → "用户登录怎么实现的"搜不到 `login()`（除非字段面撞上）；只留向量 → 精确搜 `NullPointerException` 反而可能输给语义相近但不对的代码；直接拿 bm25 分 + 余弦分相加 → 量纲失衡，一个通道永久碾压另一个。

## ⑥ store.upsert_chunks：CJK bigram 处理

文件：`ai-service/app/store.py`（L35-47, L71-114, L116-132）

```python
_CJK_RUN = re.compile(r"([\u4e00-\u9fff]{2,})")

def cjk_bigrams(text: str) -> str:
    """把连续汉字串展开为二元组序列：登录接口 -> 登录 登接 接口。ASCII 不变。"""
    def expand(match: re.Match) -> str:
        run = match.group(1)
        if len(run) == 2:
            return run
        return " ".join(run[i : i + 2] for i in range(len(run) - 1))   # (1)
    return _CJK_RUN.sub(expand, text)

    # upsert_chunks 内（L107-110）：
    conn.execute(
        "INSERT INTO chunks_fts (chunk_id, content, path, language) VALUES (?,?,?,?)",
        (chunk["id"], cjk_bigrams(chunk["content"][:8000]),            # (2)
         chunk.get("path", ""), chunk.get("language", "")),
    )

    # keyword_search 内（L117-120）：
    tokens = re.findall(r"\w+", cjk_bigrams(query))[:24]               # (3)
    if not tokens:
        return []
    match_expr = " OR ".join(f'"{t}"' for t in tokens)
```

**逐行解释**：

- (1)：正则 `_CJK_RUN` 捕获**连续 2 个及以上汉字**的片段，`expand` 把它滑窗切成交叠二元组（bigram）：`登录接口` → `登录 登接 接口`。长度恰为 2 的串直接返回。ASCII（英文、数字、下划线）完全不处理。
- (2)：**写入侧**——进 FTS5 虚拟表的内容先过 bigram 展开。FTS5 的 `unicode61` 分词器按 Unicode 词边界切词，而 CJK 字符之间没有空格，整句中文会被当成一整个超长 token，导致任何短语查询都匹配不上。bigram 化后，中文变成了空格分隔的"伪词汇"。
- (3)：**查询侧**——用户查询必须经过**同样的变换**再切词（`[:24]` 限制 token 数防 FTS 表达式过长）。这是本段最重要的工程纪律：**索引与查询的预处理必须严格对称**，否则写入的是 bigram、查询的是原文，永远匹配不上。L120 里 token 之间用 `OR` 连接——"登录 接口"任一 bigram 命中即入围，再由 bm25（L127 `ORDER BY bm25(chunks_fts)`）按命中密度排序。交叠 bigram 的副产品：`登录接口` 产生的 `登录/接口` 让**相邻词组合**的文档天然命中更多 bigram，得分更高，近似还原了词组相关性。

**设计动机**：不引入 jieba 等中文分词依赖（少一个二进制依赖、少一份词典、避免分词器版本漂移），用 20 行确定性代码解决 FTS5 不支持 CJK 词组匹配的问题。代价是索引体积膨胀（N 个字变成 N-1 个词）和英文单词内混排场景的精度损失——对代码检索场景完全可接受。

**如果去掉会怎样**：`ai-service/tests/test_api.py` L42-44 就是活证据——`README.md` 的中文内容"计算器示例项目，包含加法功能"入索引后，查询"加法功能在哪实现？"能命中；bigram 去掉后这句查询对所有中文文档**零命中**，中文用户会以为检索坏了。这也是 09 篇"中文检索不到词"排障条目的根源。

## ⑦ frontend http.ts 响应拦截器：401 的统一出口

文件：`frontend/src/api/http.ts`（L12-54）

```typescript
const http: AxiosInstance = axios.create({
  baseURL: '/api/v1',
  timeout: 180000, // AI 分析同步调用最长 ~90s，留足余量          // (1)
})

http.interceptors.request.use((config) => {
  const token = localStorage.getItem('devpilot_token')
  if (token) {
    config.headers.Authorization = `Bearer ${token}`              // (2)
  }
  return config
})

http.interceptors.response.use(
  (response) => response,
  (error: AxiosError<ApiResponse<unknown>>) => {
    const status = error.response?.status
    const body = error.response?.data
    if (status === 401) {
      localStorage.removeItem('devpilot_token')                   // (3)
      localStorage.removeItem('devpilot_user')
      if (router.currentRoute.value.name !== 'login') {           // (4)
        ElMessage.warning('登录已过期，请重新登录')
        router.push({ name: 'login' })                            // (5)
      }
    } else {
      const message = (body?.message as string) || error.message || '请求失败，请稍后重试'
      ElMessage.error(message)                                    // (6)
    }
    return Promise.reject(error)                                  // (7)
  },
)

export async function request<T>(promise: Promise<{ data: ApiResponse<T> }>): Promise<T> {
  const resp = await promise
  if (resp.data.code !== 0) {                                     // (8)
    ElMessage.error(resp.data.message || '操作失败')
    throw new Error(resp.data.message)
  }
  return resp.data.data
}
```

**逐行解释**：

- (1)(2)：全局超时 180 秒——AI 问答是**同步接口**，Java 侧最长等 Python 150s（`application.yml` L74），前端必须比整条链路的上限更长，否则后端还在算、前端已经断开。请求拦截器统一注入 Token，业务代码里永远不需要手写 `Authorization` 头。
- (3)(4)(5)：401 处理三件套：清掉本地凭证 → 判断当前是否已在登录页（**防循环重定向**）→ 跳登录页并给一句人话提示。没有 (4) 这个守卫，登录接口本身若返回 401（密码错误在网关层被误判等）会把用户困在"登录页↔刷新"死循环里。
- (6)(7)：非 401 错误统一弹后端给的 `message`（与 API_CONTRACT 的统一响应结构 `{code,message,data}` 对应），三段兜底保证总有可读文案；**处理完仍然 reject**——拦截器做了 UI 提示，但错误对象继续抛给业务代码，让"是否需要额外处理"（比如表单校验错误就地展示）由调用方决定，拦截器不越权吞错。
- (8)：第二层防线：HTTP 200 但业务 `code != 0` 的情况（后端 `ApiResponse` 包装），同样统一弹错并抛出。`request<T>()` 泛型包装让业务代码直接拿到 `data`，类型安全。

**设计动机**：认证过期是横切关注点，散落在每个页面处理必然漏。集中到拦截器后，全站 401 行为只有一个实现、一个出口；`errorMessage()` 工具函数（L56-59）再兜一层，保证 catch 块里也能拿到人话文案。

**如果去掉会怎样**：每个页面都要写 `if (err.response?.status === 401)`；漏写的页面在 Token 过期后表现为"点击无反应 + 控制台红色报错"；去掉 (4) 则登录页自身失败时反复 push 路由，`NavigationDuplicated` 报错刷屏。

## ⑧ DefectService.changeStatus：服务端状态机

文件：`backend/src/main/java/com/devpilot/module/defect/DefectService.java`（L38-43, L127-141, L183-195）

```java
/** 缺陷状态机：只允许列出的目标状态 */
private static final Map<String, List<String>> TRANSITIONS = Map.of(
        "OPEN",        List.of("IN_PROGRESS"),
        "IN_PROGRESS", List.of("RESOLVED", "OPEN"),
        "RESOLVED",    List.of("CLOSED", "OPEN"),
        "CLOSED",      List.of());                                   // (1)

@Transactional
public DefectVO changeStatus(UserPrincipal user, Long defectId, String target) {
    Defect defect = requireAccessible(defectId, user);                // (2)
    List<String> allowed = TRANSITIONS.getOrDefault(defect.getStatus(), List.of());  // (3)
    if (!allowed.contains(target)) {                                  // (4)
        throw BizException.conflict("非法状态流转: " + defect.getStatus() + " → " + target
                + "（允许: " + (allowed.isEmpty() ? "无，已终态" : allowed) + "）");
    }
    if (!canOperate(user, defect)) {                                  // (5)
        throw BizException.forbidden("仅报告人/负责人/项目管理员可以流转该缺陷");
    }
    defect.setStatus(target);
    defectMapper.updateById(defect);
    return toVO(defect);
}

private boolean canOperate(UserPrincipal user, Defect defect) {       // (6)
    if (user.isAdmin()) return true;
    if (defect.getReporterId().equals(user.id())) return true;
    if (user.id().equals(defect.getAssigneeId())) return true;
    Project project = projectService.requireAccessible(defect.getProjectId(), user);
    return project.getOwnerId().equals(user.id());
}
```

**逐行解释**：

- (1)：状态机是一张**静态不可变表**——从每个状态出发允许到达的目标列表。`CLOSED → List.of()`（空表）表达终态。数据结构选得小，语义就清楚：校验就是一次 `contains`。
- (2)：先取缺陷并做项目级访问控制（`requireAccessible` L177-181：缺陷存在 + 用户可访问该项目），越权在业务校验之前就被挡住。
- (3)(4)：查表校验。非法流转返回 **409**（`code=40900`）而不是 400——语义是"请求格式没问题，但对象当前状态不允许"；错误消息把当前允许的目标列表**回显给前端**，前端据此渲染可点按钮（API_CONTRACT 1.6 明确了这一契约）。
- (5)(6)：状态合法 ≠ 人合法。`canOperate` 的判定顺序：ADMIN → 报告人 → 负责人 → 项目 owner（最后一个同时复用了 `requireAccessible` 保证此人确实在该项目里）。注释（L32-33）点明原则：*"状态流转与操作权限都在服务端校验，前端提示仅为体验优化"*。方法带 `@Transactional`，状态写入与后续可能的联动在同一事务里。

**设计动机**：如果只靠前端隐藏按钮，用 curl 一发 `POST /defects/5/status {"status":"CLOSED"}` 就能把已关闭缺陷改成任意状态，审计链全毁。把状态机放在服务端 + 用一张声明式表表达，校验逻辑 10 行、加新状态只改一处，且 `allowedNextStatuses` 能自动反哺前端 UI。

**如果去掉会怎样**：非法流转直接写库 → 报表统计（`/stats/dashboard` 的 `defectStatus`）失真；任何人（包括无权限的项目外用户，若无 (5)）可以关闭别人负责的缺陷；"RESOLVED → OPEN 退回"这类业务规则无法追溯是谁在什么规则下放行的。

## 收尾：8 段代码的共同气质

把 8 段放在一起看，DevPilot 的工程取向相当一致——**防线放在最可信的一层**（并发防重交给数据库唯一索引（②），权限交给服务端（⑧），401 交给授权规则（①））；**不可信输入永远先限额**（zip 三重上限 + 流式读取（③）、chunk/字符多级预算（④⑤）、Token/日志脱敏截断（07 篇））；**降级要诚实**（向量挂了就说 `vectorEnabled=false`（④⑤），文件跳过就写 `skip_reason`（③），演示模式就打徽标（07 篇））；**横切关注点集中化**（认证过滤器（①）、axios 拦截器（⑦）、状态机表（⑧）——每个横切面只有一个实现）。
